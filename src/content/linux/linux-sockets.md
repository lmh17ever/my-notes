## Что такое сокет

**Сокет** — конечная точка сетевого соединения. Это комбинация:

```text
Протокол : Локальный IP : Локальный порт : Удалённый IP : Удалённый порт
```

## Два типа сокетов

| Тип | Что делает | Пример |
|-----|------------|--------|
| **Слушающий (серверный)** | Ждёт входящих соединений | `0.0.0.0:80` (nginx) |
| **Подключённый (клиентский)** | Уже установленное соединение | `185.250.180.136:54321` → `93.184.216.34:80` |

## Как отличить в ss

**Слушающий сокет (`ss -tulpn`):**

```text
LISTEN  0  128  0.0.0.0:80  0.0.0.0:*
```

**Подключённый сокет (`ss -tupn`):**

```text
ESTAB  0  0  185.250.180.136:54321  93.184.216.34:80
```

## Почему сервер использует один порт для всех

Серверный сокет слушает на одном порту (`80`), но для каждого клиента создаётся **уникальный подключённый сокет**, который различается по:

- удалённому IP (адрес клиента);
- удалённому порту (временный порт клиента).

**Важно:** сервер **не тратит** свои локальные порты на клиентов. Только клиент тратит временные порты.

## Временные (эфемерные) порты

- **Кто использует:** клиент (браузер, curl, ваше приложение).
- **Диапазон:** 49152–65535 (по умолчанию в Linux).
- **Зачем:** чтобы ядро могло различать несколько одновременных соединений от одного приложения.

## Ключевое отличие: порт vs сокет

| Порт | Сокет |
|------|-------|
| Число (например, 80) | IP + порт (например, `0.0.0.0:80`) |
| Абстрактное понятие | Конкретная конечная точка |
| Может быть только один процесс на порт | Каждое соединение — свой уникальный сокет |

## Команды

| Команда | Что показывает |
|---------|----------------|
| `ss -tulpn` | Слушающие сокеты (серверы) |
| `ss -tupn` | Установленные соединения (клиентские + серверные) |
| `ss -tulpn \| grep 80` | Найти всё, что связано с портом 80 |

## Главный вывод

> **Сервер слушает на одном порту, но обслуживает миллионы клиентов через уникальные подключённые сокеты.**

Ограничение не в портах, а в: оперативной памяти, количестве файловых дескрипторов (`ulimit -n`) и настройках ядра.

## Где пригодится в backend-разработке

Сокеты — то, из чего состоит **каждое** сетевое взаимодействие в приложении. Их понимание помогает диагностировать десятки проблем.

### Реальные сценарии

#### Сценарий 1: Слишком много открытых соединений (Too many open files)

```text
OSError: [Errno 24] Too many open files
```

Каждое соединение (сокет) в Linux — это файловый дескриптор, а ОС ограничивает их количество на процесс. Если сервис открывает соединения и **не закрывает их**, дескрипторы исчерпываются и приложение падает.

**Как диагностировать:**

```bash
sudo lsof -p <PID> | wc -l
ulimit -n
```

Решение: правильно закрывать соединения в коде (например, пулы соединений к БД) и при необходимости поднять лимит (`ulimit -n 65535`).

#### Сценарий 2: Соединения висят в состоянии TIME_WAIT

```bash
ss -tupn | grep TIME_WAIT
```

Когда соединение закрывается, оно не сразу освобождается: переходит в `TIME_WAIT` и висит ~60 секунд. Это нормально, но при **очень большом** количестве коротких соединений (приложение открывает/закрывает соединение с БД на каждый запрос) порты могут закончиться.

**Что делать:** использовать пул соединений (переиспользовать открытые сокеты); настроить ядро (`net.ipv4.tcp_tw_reuse`, `net.ipv4.tcp_fin_timeout`).

#### Сценарий 3: Приложение зависло в состоянии CLOSE_WAIT

```bash
ss -tupn
```

Много соединений в состоянии `CLOSE-WAIT` означает: клиент закрыл соединение, но приложение **не закрыло свой конец** (в коде не закрывается сокет или не завершается чтение). Со временем накапливаются тысячи `CLOSE-WAIT` сокетов → снова «Too many open files».

#### Сценарий 4: База данных не отвечает (в другой сети)

Приложение к PostgreSQL на `10.0.0.5:5432` получает `psycopg2.OperationalError: connection timed out`. Проверка `ss -tupn | grep 5432` показывает сокет в состоянии `SYN-SENT` (пытается установить соединение, но не получает ответа). Значит, проблема не в коде, а в сети или на удалённой машине.

#### Сценарий 5: Порт занят, но процесс не найден

Приложение падает с `Address already in use`, но `ss -tulpn | grep 8000` показывает `0.0.0.0:8000`. Убиваешь процесс — порт всё ещё занят. **Почему:** может быть ещё один сокет на IPv6 `[::]:8000` (другой PID). Проверь заново и убей процесс на IPv6.

#### Сценарий 6: Медленные ответы от API

Ответ от внешнего API приходит за 5 секунд вместо 100 мс. `ss -tupn | grep <IP_внешнего_сервиса>` — если сокет в состоянии `ESTAB`, но данные не передаются, проблема на стороне удалённого сервера или в сети.

#### Сценарий 7: Логи — «Connection reset by peer»

Удалённая сторона закрыла соединение без предупреждения (обычно клиент сбросил соединение до того, как сервер отправил ответ). Причины: клиент отправил запрос и закрыл соединение до ответа; истёк клиентский таймаут; клиент перезагрузился. Это **не твоя ошибка**, а поведение клиента.

### Что даёт знание сокетов

| Навык | Когда пригодится |
|-------|-------------------|
| Понять, сколько открытых соединений у приложения | Когда падает с «Too many open files» |
| Отличить состояние `ESTAB` от `TIME_WAIT` и `CLOSE_WAIT` | При диагностике утечек соединений |
| Найти висящие сокеты | Когда порт занят, но процесс не найден |
| Проверить, дошёл ли пакет до сокета | Когда сервис не отвечает |
| Диагностировать, кто разорвал соединение | При чтении логов об ошибках |

### Итог

Сокеты — это **каждое открытое соединение** в системе. Сталкиваться придётся, когда: приложение падает от перегрузки соединениями; соединения не закрываются и накапливаются; порт занят, но процесс не виден; удалённый сервер внезапно закрывает соединение.
