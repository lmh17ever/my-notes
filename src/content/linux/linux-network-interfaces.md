## Что такое сетевой интерфейс

**Сетевой интерфейс** — точка входа/выхода пакетов в ядре. Как дверь.

**Типичные имена:**

- `lo` — loopback (127.0.0.1, только для себя)
- `eth0`, `ens192`, `enp0s3` — проводные
- `wlan0` — Wi-Fi
- `docker0`, `br-*` — виртуальные мосты Docker
- `veth*` — виртуальные пары для контейнеров

**Состояния:**

- `UP` — интерфейс включён административно (приказ есть)
- `DOWN` — выключен
- `LOWER_UP` — физический сигнал есть (кабель подключён)
- `NO-CARRIER` — кабеля нет или нет соединения
- `state UP/DOWN` — итоговый статус, обобщение флагов

**Команда:**

```bash
ip link show
```

## Где пригодится в backend-разработке

Backend-разработчик редко вручную поднимает интерфейсы, но постоянно сталкивается с ситуациями, где нужно понять, на каком интерфейсе что происходит.

### Реальные сценарии

#### Сценарий 1: Приложение слушает не на том интерфейсе

Приложение запущено на порту `8080`, с другого компьютера к нему не достучаться, а на локальной машине `curl localhost:8080` работает.

**Почему так бывает:** в коде/конфиге указано:

```python
app.run(host='127.0.0.1', port=8080)
```

А нужно было:

```python
app.run(host='0.0.0.0', port=8080)
```

В первом случае приложение слушает **только на loopback-интерфейсе** (`lo`) — снаружи его не видно. `ss -tulpn | grep 8080` покажет `127.0.0.1:8080`, а не `0.0.0.0:8080`.

#### Сценарий 2: Сервер в облаке / на VPS

Есть интерфейс `ens192` с публичным IP и внутренние `docker0`, `br-*`. Знание интерфейсов помогает:

- понять, какой IP указывать в конфигах;
- понять, почему сервис доступен по одному IP, но не по другому;
- отличить публичный интерфейс от внутренних (Docker, VPN).

#### Сценарий 3: Диагностика проблем с сетью

Сервис не отвечает. `ip link show` показывает, что интерфейс в состоянии `DOWN` или `NO-CARRIER` — это указывает на проблему на уровне **физического подключения** или **настройки сети**, а не в коде.

### Что даёт знание интерфейсов

| Навык | Когда пригодится |
|-------|-------------------|
| Проверить, какие интерфейсы есть на машине | При деплое на новую среду |
| Понять, почему `127.0.0.1` работает, а публичный IP — нет | Когда приложение слушает только на localhost |
| Отличить физический интерфейс от виртуального (Docker, VPN) | Когда работаешь с контейнерами или VPN |
| Проверить состояние интерфейса | Когда сервис внезапно перестал отвечать |

### Итог

Backend-разработчик обязан уметь: проверить, какие интерфейсы есть; понять, на каком интерфейсе слушает сервис; диагностировать, почему сервис недоступен снаружи.
