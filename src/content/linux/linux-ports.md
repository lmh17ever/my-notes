Порты — это та самая «квартира», в которой живёт сервис. С ними сталкиваешься каждый день: от запуска приложения до дебага в проде.

## Реальные сценарии

### Сценарий 1: Запуск приложения — порт уже занят

```bash
python app.py
# OSError: [Errno 98] Address already in use
```

Проверяем, кто занял порт:

```bash
sudo ss -tulpn | grep :8000
```

Это старый процесс, который не завершился корректно. Останавливаем:

```bash
sudo kill -9 <PID>
```

Навык: знать, какой процесс слушает порт, как его найти и остановить.

### Сценарий 2: Приложение не стартует, потому что порт ниже 1024

```python
app.run(host='0.0.0.0', port=80)
```

```text
PermissionError: [Errno 13] Permission denied
```

Порты **1–1023** могут слушать только процессы с правами root. Решения:

- запускать с `sudo` (не рекомендуется для продакшна);
- использовать порт выше 1024 (например, 8000) и настроить Nginx как прокси;
- дать приложению права на конкретный порт (через `setcap`).

### Сценарий 3: Взаимодействие между микросервисами

- Аутентификация — порт `5001`
- Заказы — порт `5002`
- Платежи — порт `5003`

AUTH_SERVICE_URL=http://localhost:5001
ORDER_SERVICE_URL=http://localhost:5002
PAYMENT_SERVICE_URL=http://localhost:5003

Каждый микросервис должен знать порт другого (хранится в конфигах или переменных окружения). Если порт займёт что-то другое — сервис не сможет найти другой.

### Сценарий 4: Локальная разработка с несколькими проектами

Все три проекта запускаются на порту `8000` — одновременно не запустить. Решения:

- менять порт в конфиге каждого проекта;
- использовать Docker с пробросом портов:

```bash
docker run -p 8001:8000 project1
docker run -p 8002:8000 project2
docker run -p 8003:8000 project3
```

### Сценарий 5: Реальный продакшн — Nginx как прокси

Обычно приложение не слушает напрямую порт 80 или 443:

- Nginx слушает порты `80` и `443`;
- приложение слушает на `127.0.0.1:8000`;
- Nginx проксирует запросы с 80/443 на 8000.

Зачем так делать: Nginx раздаёт статику, кеширует, балансирует нагрузку, обрабатывает SSL; приложение не нужно запускать от root; можно перезапускать приложение, не разрывая соединения с клиентом (Nginx держит соединение).

### Сценарий 6: Логи и мониторинг

```text
WARNING: 185.250.180.136:54321 - "GET /api/users HTTP/1.1" 200
```

`54321` — **временный порт** клиента, его номер не важен: используется только для этого соединения и освобождается после закрытия. Если в логах **один и тот же порт** от разных клиентов — это нормально, клиентские порты могут повторяться.

### Сценарий 7: Проверка доступности порта

```bash
nc -zv localhost 5432
# Connection to localhost port 5432 [tcp/postgresql] succeeded!
```

PostgreSQL доступен. Если порт закрыт или никто не слушает:

```text
nc: connect to localhost port 5432 (tcp) failed: Connection refused
```

Это помогает быстро понять, запущена ли база данных (или Redis, другие сервисы).

## Что даёт знание портов

| Навык | Когда пригодится |
|-------|-------------------|
| Проверить, кто слушает порт | При запуске приложения, если порт занят |
| Убить процесс по порту | Когда нужно освободить порт |
| Знать, что порты \<1024 требуют root | При настройке продакшн-сервера |
| Проверить доступность порта | При диагностике подключений к БД, Redis, другим сервисам |
| Настроить проксирование (Nginx → приложение) | В продакшне |
| Отличить локальный порт от клиентского | При чтении логов и анализе трафика |

## Итог

Порты — повседневная реальность бэкенд-разработчика: запускать приложения на разных портах, проверять, кто занял нужный порт, диагностировать, почему не открывается соединение, настраивать прокси и балансировку, читать логи и понимать, что означает цифра после IP.
