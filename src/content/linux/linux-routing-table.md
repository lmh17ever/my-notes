## Что это

**Таблица маршрутизации** — набор правил, по которым ядро Linux решает, **куда отправить пакет**.

**Команда:**

```bash
ip route show
```

**Пример:**

```text
default via 185.250.180.1 dev ens192 onlink
172.18.0.0/16 dev br-85d62ae1eba7 proto kernel scope link src 172.18.0.1
185.250.180.0/24 dev ens192 proto kernel scope link src 185.250.180.136
```

## Как читать строку

| Часть | Что означает |
|-------|---------------|
| `default` | «Все адреса, которые не попали под другие правила» |
| `via X.X.X.X` | Отправить через этот шлюз (роутер) |
| `dev eth0` | Отправить через этот интерфейс |
| `185.250.180.0/24` | Правило работает для адресов из этой сети |
| `src 185.250.180.136` | В качестве отправителя использовать этот IP |
| `linkdown` | Интерфейс выключен, правило не работает |
| `onlink` | Считать, что шлюз доступен напрямую |

## Как работает принятие решения

1. Ядро смотрит на IP-адрес получателя.
2. Идёт по таблице и ищет **самое конкретное совпадение** (самую длинную маску).
3. Если находит — отправляет по этому правилу.
4. Если не находит — отправляет через `default` (шлюз по умолчанию).

## Пример

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0
```

- Пакет на `192.168.1.50` → подпадает под `192.168.1.0/24` → напрямую.
- Пакет на `8.8.8.8` → не подпадает → через `default` → шлюз `192.168.1.1`.

## Шлюз (gateway)

**Что это:** устройство (роутер), которое пересылает пакеты из одной сети в другую.

**Важно:** шлюз всегда находится в **одной локальной сети** с твоим компьютером.

**Пример:** твой IP `185.250.180.136/24`, шлюз `185.250.180.1` (в той же сети `/24`).

## Команды

| Команда | Что делает |
|---------|------------|
| `ip route show` | Показать таблицу маршрутизации |
| `ip route add default via X.X.X.X dev Y` | Добавить шлюз по умолчанию |
| `ip route del default` | Удалить шлюз по умолчанию |

## Важные выводы из таблицы

```text
default via 185.250.180.1 dev ens192 onlink
172.17.0.0/16 dev docker0 linkdown
172.18.0.0/16 dev br-85d62ae1eba7 src 172.18.0.1
185.250.180.0/24 dev ens192 src 185.250.180.136
```

- Интернет идёт через `ens192` и шлюз `185.250.180.1`.
- Сеть `docker0` неактивна.
- Контейнеры в сети `172.18.0.0/16` общаются напрямую через мост `br-85d62ae1eba7`.
- Локальные адреса `185.250.180.x` отправляются напрямую.

## Где пригодится в backend-разработке

Таблица маршрутизации — то, как ОС решает, **через какую дверь** отправить пакет. Невидима, пока всё работает, и критична, когда что-то ломается.

### Реальные сценарии

#### Сценарий 1: Сервис не может достучаться до внешнего API

```python
import requests
response = requests.get('https://api.google.com')
```

Код падает с таймаутом: DNS работает, интерфейс поднят, IP есть — а пакет не уходит. Проверка `ip route show`: если нет `default` маршрута или он указывает на неправильный шлюз — пакет не знает, куда идти за пределы локальной сети.

#### Сценарий 2: Контейнеры не видят друг друга / хост не видит контейнеры

Хост `185.250.180.136`, контейнер `172.18.0.2`, `curl http://172.18.0.2:8000` — работает, потому что в таблице есть строка:

```text
172.18.0.0/16 dev br-85d62ae1eba7 proto kernel scope link src 172.18.0.1
```

Ядро знает: адреса из `172.18.0.0/16` отправлять напрямую через мост, без шлюза. Если бы строки не было, пакет ушёл бы в `default` — в интернет — и не дошёл бы до контейнера.

#### Сценарий 3: Поднял VPN — сломалась локальная сеть

VPN часто добавляет маршрут `0.0.0.0/1` (или `default`) через свой интерфейс, и все пакеты (в том числе в локальную сеть) уходят в VPN. VPN не знает про контейнеры. Лечится удалением/изменением маршрута:

```bash
sudo ip route del 172.18.0.0/16 via 10.8.0.1
```

#### Сценарий 4: Приложение слушает на всех интерфейсах, но не достучаться снаружи

Приложение на `0.0.0.0:8000`, локально работает, с других компьютеров — нет. Причина может быть не в приложении, а в таблице маршрутизации на уровне **шлюза** или **NAT**. Чтобы диагностировать, убедись, что на машине есть маршрут до клиента.

#### Сценарий 5: Диагностика через traceroute

```bash
traceroute -n 10.0.5.10
```

Показывает, на каком шаге теряются пакеты: на твоей машине, на маршрутизаторе провайдера или в облаке.

#### Сценарий 6: Неправильный шлюз по умолчанию

Машина перезагрузилась, DHCP не сработал, `ip route show` пуст или нет `default`. Код падает с `Network is unreachable` или `No route to host`. Добавляем шлюз вручную:

```bash
sudo ip route add default via 185.250.180.1 dev ens192
```

### Что даёт знание таблицы маршрутизации

| Навык | Когда пригодится |
|-------|-------------------|
| Проверить, есть ли `default` маршрут | Когда сервис не может достучаться до внешнего мира |
| Понять, через какой интерфейс идёт трафик к конкретному IP | При диагностике сетевых проблем |
| Увидеть маршруты Docker, VPN, мостов | Когда контейнеры не видят друг друга или хост |
| Отличить локальный маршрут (`dev eth0`) от маршрута через шлюз (`via`) | При анализе, пойдёт ли пакет напрямую или через роутер |
| Удалить / изменить маршрут | Когда VPN ломает доступ к локальным ресурсам |

### Итог

Таблица маршрутизации — **карта**, по которой ядро направляет пакеты. Пригодится, когда контейнеры не видят друг друга, VPN ломает сеть, приложение не достукивается до внешнего API, или после деплоя сервис внезапно перестаёт отвечать.
