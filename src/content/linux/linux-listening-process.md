## Что это

**Listening process** — процесс (программа), которая:

- создала сокет;
- привязалась к порту;
- сказала ядру: «Я жду соединений на этом порту»;
- находится в состоянии `LISTEN`.

## Как посмотреть

```bash
sudo ss -tulpn
```

**Флаги:**

| Флаг | Что значит |
|------|------------|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | Только слушающие (LISTEN) |
| `-p` | Показать процесс (PID, имя) |
| `-n` | Не преобразовывать порты в имена (числами) |

**Почему `sudo`:** порты ниже 1024 защищены, информация о процессах тоже.

## Пример вывода

```text
tcp  LISTEN  0  128  0.0.0.0:80   0.0.0.0:*   users:(("nginx",pid=1234,fd=6))
```

| Часть | Что означает |
|-------|---------------|
| `tcp` | Протокол |
| `LISTEN` | Состояние сокета (ждёт соединений) |
| `0.0.0.0:80` | Слушает на всех интерфейсах, порт 80 |
| `nginx` | Имя процесса |
| `pid=1234` | PID процесса |
| `fd=6` | Файловый дескриптор сокета внутри процесса |

## Как проверить конкретный порт

```bash
sudo ss -tulpn | grep :8000
```

или

```bash
sudo lsof -i :8000
```

Пример вывода `lsof`:

```text
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
python3  5678 root    3u  IPv4  12345      0t0  TCP *:8000 (LISTEN)
```

## Файловый дескриптор (FD)

**Что это:** номер, который ядро выдаёт процессу при открытии файла или сокета.

**Почему важно:** сокет в Linux — это тоже «файл». Процесс обращается к сокету по этому номеру.

**Стандартные FD:**

| FD | Что |
|----|-----|
| 0  | stdin (ввод) |
| 1  | stdout (вывод) |
| 2  | stderr (ошибки) |
| 3+ | Открытые файлы и сокеты |

## Что делает процесс при «слушании»

1. Создаёт сокет (`socket()`).
2. Привязывает к порту (`bind()`).
3. Начинает ждать соединения (`listen()`).
4. Ядро запоминает: `порт → процесс`.
5. При приходе пакета ядро пробуждает процесс (`accept()`).

## Один порт — один процесс (обычно)

- Один процесс может слушать **несколько портов** (например, nginx слушает 80 и 443).
- Один порт не могут слушать **два процесса одновременно** (если не включена опция `SO_REUSEADDR`, но это редкость).

## Почему без sudo не видно процесс

Без прав root видно только:

```text
tcp  LISTEN  0  128  0.0.0.0:80  0.0.0.0:*
```

С `sudo` видно:

```text
tcp  LISTEN  0  128  0.0.0.0:80  0.0.0.0:*   users:(("nginx",pid=1234,fd=6))
```

Информация о том, какой процесс слушает порт, защищена на уровне ядра.

## Команды для быстрого поиска

| Что нужно | Команда |
|-----------|---------|
| Все слушающие процессы | `sudo ss -tulpn` |
| Кто слушает порт 80 | `sudo ss -tulpn \| grep :80` |
| Кто слушает порт 8000 | `sudo ss -tulpn \| grep :8000` |
| Альтернативный способ | `sudo lsof -i :8000` |
| Посмотреть все сокеты процесса | `sudo lsof -p <PID>` |

## Где пригодится в backend-разработке

Listening process — точка входа в сервис, ответ на вопрос **«Моё приложение вообще запущено и готово принимать запросы?»**.

### Реальные сценарии

#### Сценарий 1: Приложение запустилось, но не отвечает

```bash
python app.py
# * Running on http://0.0.0.0:8000
```

Браузер → страница не грузится. Проверка `sudo ss -tulpn | grep 8000` — **ничего нет**. Значит: приложение либо упало сразу после запуска, либо слушает на другом порту, либо зависло до вызова `listen()`.

#### Сценарий 2: Приложение висит в логах, но порт не слушает

Логи без ошибок, но `ss -tulpn` не показывает его на порту. **Причина:** приложение делает что-то тяжёлое **перед** вызовом `listen()`, например инициализирует подключение к БД, которая не отвечает:

```python
# app.py
db.connect()  # зависло на 30 секунд
app.run(port=8000)  # до этой строки не доходит
```

`ss` → порта нет → проблема в **старте**, а не в самом приложении.

#### Сценарий 3: Кто-то занял твой порт

```text
Error: listen EADDRINUSE: address already in use :::8000
```

```bash
sudo ss -tulpn | grep 8000
# tcp  LISTEN  0  128  0.0.0.0:8000  0.0.0.0:*  users:(("python3",pid=1234,fd=3))
```

Это старый процесс → остановить:

```bash
sudo kill -9 1234
```

Или, если это другой разработчик, — разобраться, почему он занял продакшн-порт в тестовой среде.

#### Сценарий 4: Приложение работает, но клиент не достукивается

```text
tcp  LISTEN  0  128  127.0.0.1:8000  0.0.0.0:*
```

Обращение по публичному IP `185.250.180.136:8000` не работает. **Причина:** приложение слушает только на `127.0.0.1` (localhost), а не на `0.0.0.0` (все интерфейсы). Исправление:

```python
app.run(host='0.0.0.0', port=8000)
```

#### Сценарий 5: Настройка Nginx — проверка, что он слушает

```bash
sudo ss -tulpn | grep :80
# tcp  LISTEN  0  128  0.0.0.0:80   0.0.0.0:*  users:(("nginx",pid=789,fd=6))
```

Nginx слушает — всё правильно. Если бы строки не было — Nginx не запущен или неправильно сконфигурирован.

#### Сценарий 6: Логи — «Connection refused»

```text
Failed to connect to api.myapp.com port 8000: Connection refused
```

**Значит:** по указанному IP и порту **никто не слушает**. Проверка `sudo ss -tulpn | grep 8000` показывает ничего → приложение не запущено.

#### Сценарий 7: Сервис упал — проверка перезапуска (systemd/supervisor)

```bash
sudo ss -tulpn | grep 8000
```

Процесс есть → всё хорошо; нет → система не перезапустила сервис, искать причину в конфиге.

### Что даёт знание listening process

| Навык | Когда пригодится |
|-------|-------------------|
| Проверить, слушает ли приложение порт | Каждый день — после запуска сервиса |
| Найти PID слушающего процесса | Чтобы убить его или отправить сигнал |
| Понять, на каком интерфейсе слушает приложение | Когда доступно локально, но недоступно снаружи |
| Проверить, перезапустился ли сервис | После падения или деплоя |
| Отличить проблему в приложении от проблемы в сети | Когда клиент получает «Connection refused» |

### Итог

Listening process — **самая повседневная проверка** бэкенд-разработчика: после каждого запуска приложения, после каждого деплоя, при диагностике любой сетевой проблемы, при настройке прокси и балансировщиков. Навык — находить слушающий процесс, определять PID и интерфейс, понимать каждую часть вывода `ss`.
