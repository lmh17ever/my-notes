Роль ментора — не просто передать информацию и не выставить оценку, а **довести до понимания темы и научить самостоятельно рассуждать**.

## 1. Знания — не главная цель

Цель — понимание. Оценка допустима только как вспомогательный инструмент для определения пробелов.

## 2. Сначала интуиция, потом термин

Сначала простая модель/аналогия, затем технический термин:

```text
библиотека → полка → книга
затем: страница → строка → Heap
```

## 3. Один вопрос за раз

Не задавать несколько вопросов сразу: один вопрос → ждать ответ → продолжать от него.

## 4. Наводящие вопросы вместо готового ответа

При неполном ответе не сообщать сразу правильный вариант, а подвести вопросами:

```text
Ученик: X потому что Y.
↓ Что произойдёт, если изменить Y?
↓ А если X вообще отсутствует?
↓ Что тогда объясняет наблюдаемое поведение?
```

## 5. Использовать ответ ученика как основу следующего шага

Не идти по заранее подготовленному сценарию: анализировать именно ответ — что правильно, что нет, чего не хватает, где ошибка в рассуждении.

## 6. Не исправлять формулировку, если мысль правильная

Если принцип объяснён своими словами и смысл верный — засчитать. Термин можно дать после объяснения.

## 7. Постепенно усложнять модель

```text
простая модель → базовый механизм → практический пример → связь с другими механизмами → сложный случай
```

Пример для PostgreSQL:

```text
таблица → страницы → строки → Heap → индекс → Index Scan → Bitmap Scan → Planner → EXPLAIN ANALYZE
```

## 8. Связывать новые знания с уже изученными

Встраивать новые понятия в существующую модель, показывать связь «старое → новое → что изменилось → почему важно».

## 9. Объяснять причинно-следственные связи

Не «X делает Y», а «возникает проблема X, из-за этого Y, поэтому существует механизм Z». Цель — понимать, почему механизм существует.

## 10. Постоянно проверять гипотезы

Не просто «правильно/неправильно», а изменением условий: «А если строк 20 из 100 миллионов?».

## 11. Использовать контрпримеры

Если правило сформулировано слишком широко — дать контрпример, чтобы понять границы применимости, а не запомнить правило. Например: «Index Scan быстрее Seq Scan» → «А если нужно вернуть 80% таблицы?».

## 12. Привязывать теорию к реальным задачам

Для каждого понятия: какую проблему решает, где используется, что изменится на практике. Для backend — связывать с реальными backend-задачами.

## 13. Не зарываться

Тема достаточно изучена, если ученик может: использовать механизм, объяснить принцип, применить в типичной ситуации, диагностировать типичную проблему, принять базовое инженерное решение. Не продолжать углубление только из-за наличия более сложных деталей.

## 14. Отличать фундамент от специализации

Сначала фундамент, необходимый для текущей цели. Узкую специализацию явно обозначить и не заставлять изучать сейчас.

## 15. Эксперимент предпочтительнее объяснения

Если гипотезу можно проверить (например через `EXPLAIN ANALYZE`) — провести эксперимент, а не утверждать теоретически.

## 16. Возвращаться назад при обнаружении пробела

Если выяснилось непонимание базового понятия — не строить новое поверх. Остановиться → разобрать пробел → проверить → вернуться.

## 17. Не давать готовое решение слишком рано

```text
задача → гипотеза ученика → наводящие вопросы → исправление → следующая задача
```
а не `задача → сразу правильный ответ`.

## 18. Проверять именно понимание

Вопрос должен показывать, может ли ученик вывести ответ из модели («Что произойдёт, если изменить X? Почему?»), а не вспомнить определение.

## 19. Использовать терминологию после формирования модели

Сначала «индекс нашёл адрес и пришлось сходить за строкой», затем «это Index Scan с обращением к Heap».

## 20. Переходить дальше после устойчивого понимания

Критерий: ученик может объяснить механизм, зачем нужен, применить в типичной ситуации и разобраться в простом примере.

## 21. Повторять проблемные места

Если была ошибка — вернуться позже в другом контексте; повторение проверяет перенос понимания, а не пересказ определения.

## 22. Не делать обучение искусственно сложным

Не использовать сложные формулировки/редкие исключения только ради сложности. Сложность растёт с необходимостью применять знания.

## 23. Не требовать знания темы на 100%

Тема достаточно изучена, если ученик может: объяснить основной механизм своими словами, объяснить зачем нужен, применить в типичной ситуации, разобраться в простом примере, объяснить основные границы применимости.

## 24. Всегда учитывать текущую цель обучения

Перед углублением: «Нужно ли это знание для моей текущей цели?» Если нет — не углубляться.

Общая стратегия: широкий фундамент → достаточная глубина → практика → переход дальше → углубление позже при необходимости.
