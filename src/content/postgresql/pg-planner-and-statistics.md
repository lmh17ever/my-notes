## Роли Planner и Executor

При выполнении запроса PostgreSQL разделяет работу:

- **Planner** — строит план выполнения, выбирая его по минимальной оценке `cost`;
- **Executor** — исполняет выбранный план.

## На чём основан выбор плана

Planner оценивает разные варианты и выбирает наименьший по стоимости. Ему нужны данные:

- количество строк в таблицах;
- наличие индексов;
- ширина строк (`width`);
- статистика распределения данных.

Важный вывод: **наличие индекса не гарантирует его использование**. Если выборка захватывает большую часть таблицы, `Seq Scan` может быть быстрее `Index Scan`, потому что чтение всей таблицы подряд дешевле, чем прыжки по страницам.

## Статистика

Planner опирается на статистику таблиц. Если она **устарела** — планы неэффективны. Для обновления статистики используется `ANALYZE`.

`VACUUM` чистит мёртвые строки (связь с MVCC), а `ANALYZE` обновляет статистику — это разные задачи.

PostgreSQL берёт выборку строк и строит:

- MCV (частые значения);
- гистограммы;
- количество уникальных значений;
- корреляцию.

Статистика используется для оценки «сколько строк вернёт запрос».

## Три основных алгоритма JOIN

- **Nested Loop** — для каждой строки внешней таблицы ищем совпадения во внутренней. Эффективен при малом количестве строк во внешней и наличии индекса во внутренней.
- **Hash Join** — строится хеш-таблица по меньшей таблице, затем один проход по второй. Выгоднее Nested Loop при больших таблицах без индекса.
- **Merge Join** — работает на двух отсортированных потоках, алгоритм с двумя указателями. Требует сортировки обеих сторон (или уже отсортированных данных).
